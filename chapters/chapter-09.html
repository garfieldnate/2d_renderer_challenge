Chapter Nine

Compositing

Every shape so far has landed on opaque paper. Real pictures are stacks of translucent things: a shadow under the type, a wash of colour over a photo, a logo dropped to half strength. paint_through can't do any of that — it assumes the thing underneath is solid. This chapter builds the general operation, the one that combines a new pixel with whatever's already there, and it turns out there are twelve ways to do it, all of them one formula. But first a smaller thing that everyone gets wrong once: how you even store a half-transparent pixel. Get that wrong and every soft edge grows a dark halo, and it took the industry years to name why.

Here is the shape of the part. Coverage answered where. This chapter and the two after it are about what colour, and the deepest question in that is what happens where a new colour meets one already on the canvas. So far the answer was always the same — the new colour wins in proportion to its coverage, painted onto solid paper. Now the thing underneath might be translucent too, or might not be there at all, and "wins in proportion" splits into a family of operators with names like atop and xor. They were worked out in 1984 by Porter and Duff in three pages, and those three pages are still exactly right.

§ 9.1 Premultiplied pixels

A translucent pixel has a colour and an alpha, the fraction of the pixel the colour covers. The obvious way to store it is the four numbers straight: red, green, blue, alpha. The obvious way is wrong, and here is the one-line reason. Sit a soft-edged red shape on nothing and ask what a pixel half inside the edge should hold. Its colour is red, its alpha is 0.5. Now let a filter average that pixel with the fully transparent one next to it — a shrink, a blur, a gradient, anything that mixes neighbours. Average the alphas: 0.25, fine. Average the colours: red and… what colour is a transparent pixel? It has none. Whatever you stored there — black is the usual default — bleeds into the average, and the red picks up a dark tint it never had. That's the halo. It's on more shipped software than you'd believe.

The fix is to store the colour already multiplied by the alpha. A pixel(r, g, b, a) holds r, g, b each scaled by a, so the half-covered red is (0.5, 0, 0, 0.5) and the transparent one is (0, 0, 0, 0) — genuinely zero, no phantom colour. Average them and you get (0.25, 0, 0, 0.25), which un-premultiplies back to pure red at a quarter alpha. The transparent pixel contributed nothing, because in this representation nothing is what it is. from_color(c, a) premultiplies, pixel_color divides back out (a transparent pixel has no colour to recover, so it reads black), and lerp_pixel is the averaging the last paragraph relied on. This isn't an optimization. It's the only representation in which filtering a picture with transparency is even defined.

§ 9.2 Source-over

Now the operation you already know, named properly. To put a source pixel on top of a destination pixel, keep all of the source, and let through the fraction of the destination the source didn't cover: over(src, dst) = src + (1 - src.a) · dst, every channel including alpha, in premultiplied form. That's it. An opaque source has src.a = 1, so nothing of the destination survives and the result is the source — which is exactly what happened every time chapter 2's paint_through laid an opaque colour on paper. paint_through was over all along, with the destination pinned opaque. Now the destination can be anything, and the same one line handles it.

features/chapter09-over.feature

Feature: Source-over
  over(src, dst) is src composited over dst: src + (1 - src.a) * dst, every
  channel including alpha. It is exactly what paint_through has done since
  chapter 2, with an opaque destination. An opaque source hides whatever is
  behind it; a transparent source changes nothing; over an opaque destination
  the result stays opaque.

  Scenario: A translucent source over an opaque destination
    Given src ← from_color(color(1, 0, 0), 0.5)
    And   dst ← opaque(color(0, 0, 1))
    Then  over(src, dst) = pixel(0.5, 0, 0.5, 1)

  Scenario: An opaque source hides the destination
    Given src ← opaque(color(1, 0, 0))
    And   dst ← opaque(color(0, 0, 1))
    Then  over(src, dst) = src

  Scenario: A transparent source changes nothing
    Given dst ← from_color(color(0, 0, 1), 0.4)
    Then  over(CLEAR, dst) = dst

  Scenario: Over nothing leaves the source alone
    Given src ← from_color(color(1, 0, 0), 0.6)
    Then  over(src, CLEAR) = src

  Scenario: Two translucent pixels stack their alphas
    Given src ← from_color(color(1, 0, 0), 0.6)
    And   dst ← from_color(color(0, 0, 1), 0.4)
    Then  over(src, dst) = pixel(0.6, 0, 0.16, 0.76)

§ 9.3 Twelve operators, one formula

Source-over is one answer to "combine these two pixels", and it's the common one, but it's not the only sensible one. What if you want the source only where the destination already is — a highlight confined to a shape? Or the destination only where the source isn't — a hole punched out? Porter and Duff's insight is that every one of these is the same equation. Each output pixel is Fa · src + Fb · dst, and an operator is nothing but its choice of the two coefficients Fa and Fb — how much of the source survives, and how much of the destination — each written in terms of the two alphas. Source-over is Fa = 1, Fb = 1 - src.a. Twelve rows of a small table, and you have the lot.

coefficients(op, a_s, a_d):        // how much source (Fa) and destination (Fb) survive
  clear    → (0,       0)          src-out  → (1 - a_d, 0)
  src      → (1,       0)          dst-out  → (0,       1 - a_s)
  dst      → (0,       1)          src-atop → (a_d,     1 - a_s)
  src-over → (1,       1 - a_s)    dst-atop → (1 - a_d, a_s)
  dst-over → (1 - a_d, 1)          xor      → (1 - a_d, 1 - a_s)
  src-in   → (a_d,     0)
  dst-in   → (0,       a_s)

composite(op, src, dst):
  (Fa, Fb) ← coefficients(op, src.a, dst.a)
  return Fa · src + Fb · dst          // every channel, alpha included

Read the table and it explains itself. src-in keeps the source scaled by the destination's alpha, so the source shows only where the destination was — the source clipped to the destination's shape. dst-out keeps the destination scaled by 1 - src.a, so it erases the destination wherever the source is opaque. xor keeps each only where the other is absent. And the two that look like typos, src and dst, throw one pixel away entirely — useful more often than you'd guess, once clipping and groups arrive in chapter 12. The scenarios pin all twelve against a half-red source and a half-blue destination, and check the two identities that keep you honest: src-over is over, and dst-over is over with the arguments swapped.

§ 9.4 Blend modes

Compositing decides how much of each pixel survives. Blending decides what colour comes out where both are present — and where source-over takes the source unchanged, a blend mode combines the two colours first. Multiply darkens, screen lightens, overlay does both at once, and a dozen more sit in the layer menu of every editor. The machinery is small: a blend mode is a function B(backdrop, source) that produces a colour, and it slots into source-over so that the blended colour appears exactly where source and destination overlap, fading to plain source-over where they don't. When the mode is normal, B returns the source and the whole thing collapses back to over — which is the first thing to test.

The twelve separable modes treat the three channels independently, so each is a one-line function of two numbers in [0, 1]. Multiply is b · s. Screen is b + s - b·s, multiply's mirror. Darken and lighten are min and max. Hard-light is multiply or screen depending on the source; overlay is hard-light with the arguments swapped; the dodges and burns are the division pair with their zero cases spelled out; soft-light has an awkward piecewise form worth copying carefully. With an opaque source over an opaque destination there's no coverage to complicate things, so the result is the blend function itself, which is how the scenarios pin each one to a single number.

blend(mode, src, dst):             // source-over, with the overlap blended first
  a_s ← src.a;  a_d ← dst.a
  Cs ← pixel_color(src);  Cb ← pixel_color(dst)
  B  ← blend_color(mode, Cb, Cs)   // the blend function, per channel or whole-colour
  out.rgb ← a_s·(1 - a_d)·Cs + a_s·a_d·B + (1 - a_s)·dst.rgb
  out.a   ← a_s + a_d·(1 - a_s)
  return out

§ 9.5 The four that mix whole colours

Four modes at the bottom of the menu — hue, saturation, colour, luminosity — can't be done channel by channel, because they're about properties of the colour as a whole. You can't compute "the hue of the source with the brightness of the backdrop" one channel at a time; brightness is a weighted sum of all three. So these four need three small helpers from the compositing spec, and they're worth writing once because they're a tidy little bit of colour science. Lum(C) is a colour's brightness, 0.3R + 0.59G + 0.11B. Sat(C) is how far its channels spread, max − min. set_lum shifts a colour to a target brightness and clips it back into range without changing its hue; set_sat stretches it to a target saturation. From those, each mode is one line: colour is the source's hue and saturation at the backdrop's brightness, luminosity is the reverse, and hue and saturation take one property from each. This is how you tint a photo without darkening it, and it's four lines once the helpers exist. Here are the helpers in full, because the clipping in set_lum and the stretch in set_sat are the fiddly parts and the book doesn't leave them to prose:

Lum(C) ← 0.3·R + 0.59·G + 0.11·B
Sat(C) ← max(R, G, B) − min(R, G, B)

clip_color(C):                         // pull a colour back into [0, 1] around its own brightness
  L ← Lum(C);  n ← min(C);  x ← max(C)
  if n < 0:  C ← L + (C − L) · L / (L − n)      // per channel
  if x > 1:  C ← L + (C − L) · (1 − L) / (x − L)
  return C

set_lum(C, L):
  return clip_color(C + (L − Lum(C)))            // shift every channel, then clip

set_sat(C, s):                         // stretch the mid and max channels, floor the min at 0
  sort the channels into min ≤ mid ≤ max
  if max > min:  mid ← (mid − min) · s / (max − min);  max ← s
  else:          mid ← 0;  max ← 0
  min ← 0
  return C

hue        ← set_lum(set_sat(Cs, Sat(Cb)), Lum(Cb))
saturation ← set_lum(set_sat(Cb, Sat(Cs)), Lum(Cb))
color      ← set_lum(Cs, Lum(Cb))
luminosity ← set_lum(Cb, Lum(Cs))

The x > 1 branch of clip_color is easy to drop and easy to miss: plenty of colour pairs never overflow, so a version without it passes until a bright backdrop and a bright source push a channel past 1, and then that channel blows out. A scenario feeds it exactly such a pair so the branch can't be skipped.

The trap

Two shapes that abut along an edge — a country and its neighbour on a map, two faces of an unfolded box — each cover about half of every pixel along that shared edge. Paint the first: the seam pixels come out half covered, alpha 0.5. Composite the second over it, also half covering those pixels: source-over gives 0.5 + 0.5 · 0.5 = 0.75. Not 1.0. A quarter of the background shows through a line that should have been solid, and you get a faint seam down every shared edge in the picture. This is conflation: coverage and opacity are different things that both live in the alpha channel, and compositing treats the two half-covered pixels as two independent translucent layers when really they're two halves of one opaque surface. Every production renderer has this bug. The honest fixes are expensive — render the shapes into one coverage buffer before compositing, or supersample the seam — and most software lives with it. The book shows you the seam plainly rather than pretending it isn't there, because the first step to a fix you can afford is seeing the thing for what it is.

§ 9.6 Putting it together

The plate is the whole family in one picture: a blue square as destination, an orange circle as source, and each of the twelve operators applied to the pair. A layer is a buffer of premultiplied pixels — paint a shape into it through its coverage, the way chapter 2 painted colour through coverage, and now the transparent parts are genuinely transparent instead of paper-coloured. Composite two layers pixel by pixel with an operator, then flatten the result over paper with flatten_layer to see it. Read the table and every operator's definition is in front of you at once.

DST_COLOR ← color(0.2, 0.5, 0.85)    // the square: blue
SRC_COLOR ← color(0.95, 0.55, 0.1)   // the circle: orange
TILE ← 64

dst_layer():                                        // a blue square, transparent outside it
  l ← layer(TILE, TILE)
  sq ← polygon(point(10, 10), point(42, 10), point(42, 42), point(10, 42))
  paint_shape(l, fill_path(sq, "nonzero", TILE, TILE), DST_COLOR)
  return l

src_layer():                                        // an orange circle, transparent outside it
  l ← layer(TILE, TILE)
  paint_shape(l, fill_path(circle_path(38, 38, 20, 48), "nonzero", TILE, TILE), SRC_COLOR)
  return l

porter_duff_table():
  src ← src_layer();  dst ← dst_layer()
  for op, i in the twelve operators:
    tile ← flatten_layer(composite_layers(op, src, dst), PAPER)
    place tile at column i mod 4, row i / 4
  return the 4×3 grid

plate_09():
  return magnify(porter_duff_table(), 2)

The blend strip and the seam are the same shapes. blend_strip() is the identical two layers, sixteen tiles this time, each blend(mode, src, dst) per pixel and then flattened over paper — note that the square and circle are painted into layers, transparent outside their shapes, so a blend mode where the destination isn't present fades to plain source-over rather than reacting to a phantom black backdrop. seam() is two opaque triangles on an 80×80 canvas, polygon(point(4, 4), point(76, 76), point(4, 76)) and polygon(point(4, 4), point(76, 4), point(76, 76)), each painted at SRC_COLOR and composited src-over onto an opaque-paper layer, magnified by 4 so the one-pixel seam is visible.

Twelve operators, sixteen blend modes, and one leak the model can't paper over. That's the machinery of paint combining with paint. What's missing is the paint itself: so far a shape has always been one flat colour. Chapter 10 makes colour a function of position — gradients, then patterns, then in chapter 11 whole images — and every one of them ends up composited by exactly the operators you wrote here.
