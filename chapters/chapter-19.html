Chapter Nineteen

Shaping, a Field Guide

Set the word office with chapter 18 and look at the two f's. The first is fine. The second collides with the dot of the i, because the f's hook reaches over into the next glyph's space and the i's dot is exactly there. Roboto knows about this too: it has a glyph called f_i, drawn as one piece with the dot absorbed into the hook, and a rule that says when an f is followed by an i, use it. Chapter 18's layout_run never asked, because it went from characters to glyphs with a single lookup in the cmap, one in and one out. That lookup is a lie the Latin alphabet lets you get away with. For the word book in Arabic, the same four letters change shape depending on their neighbours, one of them refuses to connect to the letter after it, a vowel mark sits under the first letter without taking up any width, and the whole thing reads from the right. The step between a string and a list of glyph names is called shaping, and this chapter builds a small, honest one.

Honest means scoped. The general shaper is HarfBuzz, it's the work of a lifetime, and every browser and operating system you own carries a copy. This chapter builds the shape of it: a pipeline of small steps over a buffer of glyphs, each step driven by a rule table from the font, with the one idea that makes any of it usable, the cluster, carried through from start to finish. You'll shape one Latin ligature and one Arabic word correctly, from real tables, and know exactly what you left out.

§ 19.1 Itemizing

A string isn't one run. Book: كِتاب. is two: a Latin run in Roboto that reads left to right and an Arabic run in a different font that reads right to left, and each has its own rules. Cutting a string into runs of one script and one direction is itemizing, and it comes before everything else. script_of(codepoint) answers "arabic" for the Arabic block, "latin" for the Latin letters, and "common" for everything with no script of its own: spaces, digits, punctuation. itemize(text) cuts where the script changes, and the common characters go with the run before them, since a comma after an Arabic word belongs to that word. Each item knows its start, its end, its text, its script and its direction, which is "rtl" for Arabic and "ltr" otherwise.

§ 19.2 The glyph buffer, and clusters

Shaping doesn't work on the string. It works on a buffer of glyphs that starts out as the string's characters looked up in the cmap, one each, and gets rewritten step by step until it's the glyphs to draw. glyph_buffer(font, text) makes the starting buffer. Each entry has a glyph name and a cluster: the index of the character it came from. Right now that's boring, entry i has cluster i. The rest of the chapter is what happens to the clusters when the entries stop lining up with the characters, and the rule is always the same: when several things become one, the one keeps the smallest cluster of the several. A cluster boundary is a place the cursor is allowed to stand, and every text bug you have ever seen in an app, the cursor that lands in the middle of a letter, the selection that highlights half a glyph, the backspace that eats two characters, is somebody having lost track of them.

§ 19.3 Ligatures: substitution

Now the f and the i. Roboto's file has two ligature rules, f i → f_i and f l → f_l, in the ligatures section chapter 16 told you to expect, each a list of parts and a result. apply_ligatures(font, buffer) walks the buffer from the left. At each position it tries the rules, longest first, and if the glyphs there match a rule's parts it replaces them with the result, which takes the first part's cluster, then steps past the result and carries on. A result is never fed back into another rule, and the walk is greedy: in office the first f looks at the second f, finds no rule, and is left alone, and it's the second f that ligates with the i. The buffer comes out five glyphs long with clusters 0, 1, 2, 4, 5. Character 3, the i, has no cluster of its own any more, and that's correct: there is no longer anywhere between the f and the i for a cursor to be. Roboto's two rules are both two glyphs long, so the last scenario writes a font by hand with an a b rule, an a b c rule and an a_b a rule whose input is another rule's output, and pins that the longer one wins and that the output is never fed back.

In the real format this is one lookup type of a table called GSUB, the glyph substitution table, which has half a dozen more: single substitutions, one glyph for another; alternates; and contextual rules that apply a substitution only when the glyphs around it match a pattern. The next section uses the single kind. The contextual kind is where the lifetime goes.

§ 19.4 Arabic: joining, and the four forms

Arabic is cursive. Most letters connect to their neighbours, and a letter has a different shape depending on whether it connects to the one before it, the one after it, both, or neither: its isolated, initial, medial and final forms. The font has a glyph for each form, and which one to use is not the font's decision. It's a property of the characters, published by Unicode as a table of joining types: a dual letter joins on both sides; a right-joining letter (alef, dal, reh, waw and a few others) joins only to the letter before it, and so can never be initial or medial; a non-joining character never joins; and a transparent character, which is what the vowel marks are, is invisible to the letters either side of it. The book's Arabic font is DejaVu Sans, cut down to its Arabic in reference/chapter-19/dejavu-arabic.json, and its file carries three optional sections chapter 16's loader reads when they're present. The first is joining, Unicode's table copied for the characters in the file, so you don't have to ship the Unicode database to read one word.

The rule, then. A letter joins backward when it's dual or right-joining and the nearest non-transparent character before it is dual. It joins forward when it's dual and the nearest non-transparent character after it is dual or right-joining. Both is medial, backward alone is final, forward alone is initial, neither is isolated. arabic_forms(font, text) answers a form for every character of the text. Take كتاب, kitab, a book: kaf, teh, alef, beh. The kaf is initial. The teh joins both ways: medial. The alef joins backward but, being right-joining, never forward: final. And the beh, though it's dual, has an alef before it that won't connect, so it's isolated in the middle of a word. Put a kasra under the kaf and nothing changes, because the kasra is transparent and the kaf still sees the teh through it.

The second section is forms: for each glyph, the names of its initial, medial and final glyphs, which in the real format is GSUB's single substitution under the feature tags init, medi and fina. apply_forms(font, text, buffer) swaps each glyph for its form's glyph when the table has one and leaves it alone otherwise: alef has only a final form, marks have none. Then the ligatures run, because Arabic has a mandatory one: lam followed by alef is written as a single glyph, and DejaVu's rules say so in terms of the forms, lam.medi alef.fina → lam_alef.fina. Order matters. Forms first, then ligatures, on the glyphs the forms produced.

§ 19.5 Marks: positioning

The kasra is a short stroke under the letter it belongs to. It has an advance of zero, so the pen doesn't move for it, and it has no place of its own: it sits wherever the letter says. The third section is how the letter says it. Every mark glyph has an anchor, a point in font units, and an anchor class, "above" or "below"; every base glyph has an anchor per class. Attaching a mark means moving it so that its anchor lands on the base's anchor of the same class. That's the whole of the real format's mark-to-base positioning, a table called GPOS, minus the parts where marks stack on other marks. attach_marks(font, buffer) finds each mark's base, the nearest non-mark before it, sets the mark's offset to the base's anchor minus the mark's anchor, and gives the mark the base's cluster: the letter and its vowel are one thing as far as the cursor is concerned. A mark whose base has no anchor of its class, or with no base before it at all, stays where it is with an offset of zero.

shape(font, text) is the pipeline for one run: the buffer, then forms if the font has a forms table, then ligatures, then marks if it has a marks table. Roboto has neither, so shaping Latin comes down to the ligature pass, and the same function does both scripts. One simplification to own up to: a mark sitting between two glyphs keeps them from matching a ligature rule, because the rule wants them next to each other. HarfBuzz skips marks while it matches. This shaper doesn't, and the hand-written font's scenario in the next section pins what it does instead.

§ 19.6 Positioning, in either direction

The buffer is done. position(font, buffer, size, x, y, direction, kerning) turns it into chapter 18's placements, one per entry, in the buffer's own order. For left to right the pen starts at x and walks right, exactly as layout_run's did, kern pairs and all, and a buffer straight from the cmap positions to the same numbers. For right to left the pen starts at x plus the buffer's total advance and walks left, subtracting each advance before placing the glyph, so the first entry lands at the right end and the run still occupies x to x + advance. Marks never move the pen: a mark is placed at its base's origin plus its offset, scaled to pixels with dy turned over, which works the same in either direction because the base is wherever the pen put it. HarfBuzz reverses the buffer for right-to-left runs instead and lets the pen always walk right; either way the picture is the same, and the placements go to draw_run unchanged, which is the seam from chapter 18 doing its job. Kern pairs are between consecutive non-marks: a mark between two letters has no advance, so it can't be the pen's business, and the pair on either side of it still applies. Neither real font can show that (DejaVu's Arabic has no kern pairs and Roboto has no marks), so the hand-written font does.

Two things fall out. caret_offsets(buffer, length) is the list of character offsets a cursor may stand at: every cluster start, and the end. caret_positions is the x of each: for left to right, the origin of each cluster's first glyph and then the pen after the last; for right to left, the right edge of each cluster's first glyph, origin plus advance, and then x. Either way the caret sits on the glyph's kerned edge. For office that's six positions for six characters, none of them between the f and the i. For كِتاب it's five positions that run from right to left, the first at the run's right end and the last at x, and none of them under the kasra.

Feature: Positioning, in either direction, and where the cursor may stand
  position(font, buffer, size, x, y, direction, kerning) turns a shaped
  buffer into chapter 18's placements, one per entry in the buffer's own
  order. For "ltr" the pen starts at x and walks right, exactly as
  layout_run's does, kern pairs included. For "rtl" the pen starts at x
  plus the buffer's advance and walks left, so the first entry lands at
  the right end and the run still occupies x to x + advance. A mark never
  moves the pen: it is placed at its base's origin plus its offset scaled
  to pixels, dy turned over. buffer_advance(font, buffer, size, kerning)
  is the pen's total movement: every non-mark's advance, plus the kern
  pair between consecutive non-marks. caret_offsets(buffer, length) lists
  the character offsets a cursor may stand at: every cluster start, then
  the text's length. caret_positions(font, buffer, length, size, x,
  direction, kerning) is the x of each, in the same order: for ltr the
  origin of each cluster's first glyph, then the pen after the last glyph;
  for rtl the RIGHT edge of each cluster's first glyph, its origin plus its
  advance, then x. Either way a caret sits on the kerned edge of the
  glyph, so the first position is the run's start and the last its end.

In the GUI

InDesign's OpenType menu, under the Character panel's flyout, is a checkbox per GSUB feature tag: Standard Ligatures is liga, Discretionary Ligatures is dlig, Contextual Alternates is calt. CSS exposes the same set through font-feature-settings: "liga" 0, which turns the f_i back into an f and an i.

§ 19.7 What was left out

The trap

Figure 19.5 sets Book: كِتاب, again. by itemizing it, shaping each item in its own font and placing the items one after another. Look at the comma. It followed the Arabic word, so itemize gave it to the Arabic run, the run reads right to left, and the comma came out on the word's left, where it separates the wrong two words. Nothing in this chapter is wrong; something is missing. Deciding which way a comma between two directions faces is the bidirectional algorithm, Unicode Annex 9, which resolves every neutral character to a direction from its context, nests runs inside runs (an English word in an Arabic sentence in an English paragraph), and reorders them for display. It's longer than this chapter. So are Annex 29, which says where the boundaries between user-perceived characters are when the string itself has combining marks and emoji sequences (this chapter got away with clusters because one font's rule tables decided them), and Annex 14, which is where you may break a line when the text has no spaces or has hyphens, dashes and quotation marks with opinions. Chapter 18's break_lines is what Annex 14 looks like with every rule but one removed. All three are implemented, well, in ICU and in the libraries that wrap it, and the right thing to build here is the knowledge of what they're for.

§ 19.8 Putting it together

The plate is the chapter's whole argument in one picture: characters in on the top row, one glyph each straight from the cmap; glyphs out on the bottom row, shaped and positioned; and a line from each character to the cluster it ended up in. On the left the lines converge where two characters became one glyph. On the right they cross, because the run reads the other way, and the kasra's line joins the kaf's.

cluster_plate():
  lat ← load_font(roboto.json);  ar ← load_font(dejavu-arabic.json)
  c ← canvas(540, 210) filled with paper;  size ← 52
  for font, text, direction, x in (lat, "office", "ltr", 20), (ar, kitab, "rtl", 290):
    s ← size / font.units_per_em;  raw ← glyph_buffer(font, text)
    pen ← x;  centers ← []                                    // top row, baseline 80
    for e in raw:
      w ← max(advance(e.glyph) × s, 12)
      dim box from (pen, 34) to (pen + w, 92);  draw e.glyph gray, its origin at pen + (w − advance × s) / 2 on 80
      append pen + w / 2 to centers;  pen ← pen + w + 14
    buffer ← shape(font, text);  run ← position(font, buffer, size, x, 180, direction, true)
    boxes ← {}                                                 // bottom row, baseline 180
    for e, p in buffer, run if e is not a mark:
      widen boxes[e.cluster] to cover p.x .. p.x + advance(e.glyph) × s
    for e, p in buffer, run:
      draw_run(c, font, [p], size, magenta if e is a mark or e.glyph is not in raw else gray, true)
    for lo, hi in boxes: cyan box from (lo, 134) to (hi, 192)
    for i in 0 .. length(text) − 1:
      lo, hi ← boxes[the largest cluster start ≤ i]
      magenta hairline 0.75 wide from (centers[i], 92) to ((lo + hi) / 2, 134)
  return c

plate_19():
  return cluster_plate()
