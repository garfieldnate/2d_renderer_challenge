Chapter Twenty

Rendering SVG

Here is the first shape in the Ghostscript tiger, the drawing every 2D renderer is eventually asked to draw: m-122.3,84.285s0.1,1.894-0.73,1.875c-0.82-0.019-17.27-48.094-37.8-45.851,0,0,17.78-7.353,38.53,43.976z. It's one whisker. Try splitting it on spaces: there aren't any. Try splitting it on commas and you get 1.894-0.73, which is two numbers, and -0.82-0.019-17.27-48.094-37.8-45.851, which is six. The letters are commands, the s borrows a control point from a curve that isn't written down, and none of it is in the coordinates the canvas uses. There are 239 more paths like this one. By the end of the chapter all of them will be on your screen, and you won't have written a single new way to put a pixel down.

That's the point of this chapter, and of the book. SVG is a file format for exactly the things you've built: paths, fills, strokes, gradients, clips and groups, each with a transform. The tiger doesn't need a renderer written for it. It needs the nineteen chapters you've already got, and a front end that reads four little languages hiding in the file's attributes: numbers, path data, the transform list and style declarations. Everything past those four is plumbing, and most of the plumbing is deciding which earlier chapter to call.

§ 20.1 The document

An SVG file is XML, and XML is a solved problem that teaches nothing, so use your language's library for it. The chapter asks four things of what the library hands back. parse_xml(text) is the root element. An element's name is its local name, with the namespace taken off: SVG files declare xmlns="http://www.w3.org/2000/svg", some write every tag as svg:path, and your code shouldn't care. attribute(el, name) is an attribute's text exactly as written, or none. children(el) is the child elements in order, without the whitespace and comments between them. And find_by_id(root, id) searches the whole document, because a shape may use a gradient that's defined three hundred lines further down.

The documents

Three files live in reference/chapter-20/. tiger.svg is the Ghostscript tiger, the traditional test image that has shipped with Ghostscript for decades, in the widely circulated SVG conversion: 240 paths in nested groups, fills and hairline strokes. harbor.svg and rose.svg were drawn for this book to use everything else the chapter reads, which the tiger doesn't: basic shapes, gradients, clips, opacity, dashes, the whole transform grammar. None of them uses a DOCTYPE, entities, CSS style sheets, <use> or <text>.

§ 20.2 Numbers

Every attribute this chapter parses is numbers with something between them, and SVG is stingy with the somethings. A number is an optional sign, some digits, an optional point and more digits, and an optional exponent. The trick is noticing where one number ends: at anything that couldn't continue it. A sign can't appear in the middle of a number, so 30-40 is thirty and minus forty. A second point can't either, so .5.5 is a half and another half. An e is the start of an exponent only if a digit follows (after an optional sign); 1e is a one and then something that isn't a number at all. Between numbers you may find whitespace, and at most one comma.

read_number(s, i) reads one number from index i and answers it with the index right after it, so the caller can carry on from there. number_list(s) reads as many as it can and stops at the first thing that isn't one, which is how viewBox, points and the insides of a transform function are all read. There's one more reader, and it exists for a single reason: the arc command has two flags, each a lone 0 or 1, and the grammar lets you pack them against the next number with no separator at all. read_flag(s, i) reads exactly one character.

§ 20.3 Path data

The d attribute is a list of commands, each a letter followed by its numbers. M moves, L draws a line, H and V draw horizontal and vertical lines with one number, C is a cubic (two control points and an end), Q a quadratic (one and an end), A an elliptical arc, and Z closes. A lower-case letter means the same command with every coordinate relative to the current point. And then the shorthands, which exist because people once wrote these by hand and saved bytes wherever they could.

The first is repetition. After a command's numbers, more numbers mean the command again: L 1 1 2 2 3 3 is three lines. Moves are the exception, because a second move in a row would be pointless: the numbers after an M are lines, and after an m, relative lines. The second is the smooth curves. S is a cubic whose first control point isn't written: it's the previous cubic's second control point reflected through the current point, which is what makes the join smooth. If the command before wasn't a cubic there's nothing to reflect, and the missing point is the current point. T does the same for quadratics, and because a T's reflected point becomes the next T's previous point, a run of Ts is a whole smooth curve from a single control point.

path_commands(d) reads all of this and hands back a plain list in six commands only, M L C Q A Z, every coordinate absolute. H and V become L, S and T become C and Q with their borrowed points filled in, repeats are spelled out, and Z puts the current point back where the subpath began, so a relative command after a Z measures from there. The arc's radii come back as their absolute values, as the spec says to take them. After this function nothing else in the chapter ever sees a lower-case letter, and that's the point of doing it first.

What to do with a broken path is also in the spec, and it's generous: draw everything up to the first thing you can't read, and stop there. A path that doesn't begin with a move isn't a path. An argument group cut short is dropped, and so is everything after it.

The trap

A path-data reader written from intuition splits on spaces and commas and reads a number out of each piece. It handles M 10 20 L 30 40, and every example in every tutorial, and it reads about ninety-five files in a hundred. The tiger isn't one of them: the whisker in the opening paragraph has minus signs as its only separators, and elsewhere in the file are .5.5-style runs and relative commands chained twenty groups long. The file that breaks the next reader will have a1 1 0 0110 0, which is legal and means radius one, one, rotation zero, flags 0 and 1, and an end point of 10, 0: the flags are one character each and nothing separates them from the number after. The only reliable reader is the one that knows, at every character, what the grammar expects next, and that's the one this section builds.

§ 20.4 From commands to a path

Five of the six commands have homes already. M and L are chapter 5's move_to and line_to, Z is close, and C and Q are chapter 8's curves. The arc is the odd one out. Chapter 8 turned an arc into its center, radii and angles, and you could flatten that directly, but the walker is about to push every shape through a matrix, and an ellipse through a skew is a different ellipse whose parameters you'd have to work out again. Cubics don't have that problem: transform the control points and you've transformed the curve. So the arc becomes cubics.

A cubic can't be an arc exactly, but it can get extremely close over a quarter turn or less. For a piece of a unit circle from angle θ to θ + d, put the control points on the tangent lines at each end, 4/3 · tan(d/4) along them. For a quarter circle that's 0.5523 of a radius, the number every renderer on earth has hard-coded somewhere, and the curve strays from the circle by less than three hundredths of a percent. arc_cubics takes an arc's SVG form, lets chapter 8 find the center, cuts the swept angle into equal pieces no bigger than a quarter turn, and builds each piece on the ellipse's own axes. The first and last points are the arc's endpoints exactly, not recomputed with a cos that's off in the last bit, so the path doesn't sprout a microscopic extra segment where the arc joins its neighbours. Two degenerate cases come from the spec: an arc from a point to itself isn't drawn, and an arc with a zero radius is a straight line.

build_path(cmds, m, tolerance) walks the commands with a current point and builds a chapter 5 path in device space. Points go through the matrix. Curves go through the matrix and are then flattened, in that order, which is chapter 8's rule and matters more here than anywhere: the tiger is scaled up almost four times on its way to the canvas, and a whisker flattened at its own size would come out as a row of visible corners. The tolerance is 0.1 of a pixel, as it was for type. A subpath that's nothing but its move is dropped, because it has no geometry and a stroke would otherwise put a round cap on it.

One more function reads the commands: commands_bounds, the tight box of the geometry in user space, which a gradient needs in § 20.9. It's chapter 8's curve_bounds over every curve, arcs included once they're cubics, not the looser box of the control points.

§ 20.5 The transform attribute

Any element may carry a transform, a list of functions that becomes one of chapter 4's matrices. translate, scale and rotate are the ones you'd expect, with a one-number translate(tx) meaning no vertical move and a one-number scale(s) meaning both axes. rotate(a cx cy) turns about a point, which is translate, rotate and translate back. skewX and skewY are chapter 4's shear. matrix(a b c d e f) is the raw six numbers, listed column by column, so a b c d e f goes into the matrix as a c e over b d f; this is the single most transposed line of code in the history of SVG. Angles are in degrees here, where chapter 4 was in radians, and positive is clockwise on the screen, which is the same direction chapter 4 already turned.

The functions multiply in the order they're written, left to right. The consequence is the one chapter 4 spent a trap on: the rightmost function touches a point first. translate(10,20) scale(2) doubles a point and then moves it. An attribute that doesn't parse, whether that's an unknown function, the wrong number of numbers, or a missing parenthesis, is the identity, as if it weren't there.

§ 20.7 Basic shapes

SVG has six shapes besides path, and the spec defines every one of them as a path with the same geometry. shape_commands(el) writes that path, so nothing after it has to know there was ever a rect. A rectangle is four corners, clockwise on the screen, closed. With rounded corners it's four sides joined by four quarter arcs, the radii capped at half the width and half the height, and one radius standing in for the other if only one is given. Circles and ellipses are four quarter arcs starting at the right-hand point and running clockwise through the bottom. A line is a move and a line; polyline reads its points with number_list and polygon closes what polyline draws. A shape with a zero or negative size isn't rendered, so it has no commands, and neither does anything that isn't a shape.

The direction matters more than it looks. A clockwise rectangle has positive winding in chapter 5's convention, and a shape that punches a hole in another by running the other way only works if everyone agrees which way this way is.

§ 20.8 viewBox and preserveAspectRatio

The tiger's coordinates run from about −170 to 400, and the canvas is 450 pixels square. The root element's viewBox says which rectangle of user space should fill the canvas: four numbers, its corner and its size. If the rectangle and the canvas have the same shape, that's a scale and a translation. If they don't, preserveAspectRatio decides. none stretches each axis on its own, and circles become ellipses. Anything else keeps one scale for both axes: meet, the default, picks the smaller of the two so the whole box fits and leaves bars of paper on the spare axis; slice picks the larger so the canvas is covered and lets the box spill off the edges. The first word says where the box sits in the space left over, xMin, xMid or xMax across, glued to YMin, YMid or YMax down. view_box_matrix is all of that as one matrix, which becomes the walker's starting point.

§ 20.9 Paint servers

fill="url(#sky)" points at a linearGradient or radialGradient element, which SVG calls a paint server, and chapter 10 already has both gradients. What's missing is where they are. A gradient's coordinates can live in one of two spaces. With gradientUnits="userSpaceOnUse" they're ordinary user-space coordinates, like a shape's. With objectBoundingBox, the default, they're fractions of the shape they're painting: x1="0" x2="1" runs from the left of the shape's bounds to the right, whatever size it is, which is how one gradient can paint forty different shapes. Either way the gradient can carry its own gradientTransform.

That's three matrices, and chapter 10's gradients take device coordinates. The bridge is one small paint: transformed_paint(paint, m), which answers the inner paint's colour at inverse(m) of the point it's asked about. Walk backward from the pixel to the gradient's own space, the way chapter 11 walked from the pixel back into the image. It joins chapter 10's registry of paint kinds the way chapter 11's image did, and then any paint can be put through any matrix, a radial gradient through a squash included, which is how SVG gets elliptical gradients without defining one. paint_server builds the matrix, the element's own times the bounding box's (when it applies) times the gradient transform, reads the stops, and wraps chapter 10's gradient in it. The degenerate cases are all written into the spec, and all of them come up: no stops is nothing, one stop is a solid colour, a gradient whose two points coincide paints its last stop, and a bounding-box gradient on a shape with no width or no height has nowhere to live.

The stops are a small parser of their own. Each <stop> has an offset, a number or a percentage, clamped into [0, 1] and never allowed to go backward (a stop with a smaller offset than the one before it is moved up to meet it, which makes a hard edge, and harbor.svg uses exactly that for the lighthouse's stripes). Its colour is its stop-color property, from an attribute or a style declaration like any other property. SVG also has stop-opacity, and chapter 10's gradients paint opaque colours, so the book doesn't read it.

§ 20.10 The walker

Now the tree. render_svg(text, width, height) parses the document, makes a transparent chapter 9 layer the size of the canvas, and walks from the root, carrying two things down: the parent's style, starting from initial_style(), and a matrix, starting from the viewBox. Each element computes its style against its parent's and multiplies its own transform onto the matrix. Then a group walks its children, in document order, which is the painter's algorithm and the whole of SVG's notion of depth; and a shape draws itself. Elements that aren't a group or a shape are skipped with everything inside them: defs exists to hold things that are only drawn when something points at them, and so do gradients and clip paths, and anything the book doesn't read (title, text, whatever the editor that saved the file felt like adding) is quietly left out. At the end the layer is flattened over white paper, because an SVG's background is transparent and a PPM's can't be.

A shape draws its fill and then its stroke, each through draw_coverage, which is paint_fill aimed at a layer: sample the paint at the pixel center and composite it over what's there at coverage times the opacity. The fill is the easy half: build the device path, fill it under fill-rule. The stroke has a catch you've met before. SVG says the pen lives in user space, so under scale(2 1) a line two units wide is four pixels wide going up and two going across, and a dash pattern is measured in user units too. Chapter 4's trap was exactly this. The answer is to take the device path back through the inverse of the matrix, which puts the flattened points in user space; dash there, stroke there with chapter 13, and bring the outline forward through the matrix to fill it. Flattening still happened in device space, so the tolerance is still a tenth of a pixel. A matrix with no inverse, scale(0), squashes the shape to nothing, and nothing is what it draws.

§ 20.11 Clips and group opacity

Chapter 12 built both of these, and SVG needs one detail about each. A clipPath element holds shapes, and its clip is the union of their silhouettes, each filled under its own clip-rule. Union is chapter 9's alpha: one silhouette over another covers 1 − (1 − a)(1 − b), which is 0.75 where two half-covered edges overlap and exactly 1 wherever either is solid. clip_coverage builds the clip in the user space of the element that asked for it, its own transform included, then the clipPath's transform, then each child's. A clipPath with no shapes clips everything away; a clip-path that names nothing clips nothing.

And opacity, unlike fill-opacity, belongs to the element as a whole. A shape with both a fill and a stroke at opacity="0.5" is drawn opaque into a fresh layer and the layer is faded, so the fill doesn't show through the stroke. A group at half opacity flattens its children first and fades the result, which is chapter 12's Plate: it isn't the same picture as fading each child. So the walker's rule is: an element with an opacity below 1, or a group with a clip, draws into its own transparent layer, which is masked by the clip (mask_layer, every premultiplied channel times the coverage under it) and put over the layer below with chapter 12's pop_group_with_opacity. A plain shape with a clip doesn't need a layer: it multiplies the clip into its own coverage and paints.

render_svg(text, width, height):
